# Space Cadet 2026 plan

Date: 2026-10-20. Status: Phases A (#51 to #53), B (#55 to #59) and C (#61 to #63) are done and merged, and so is the move to C++23 (#64); Phase D is done (#66, #68, #69, #70), awaiting review. The modernization stack is merged ([modernization plan](2026-10-18-modernization.md)); item 16 of [the follow-ups plan](2026-10-19-follow-ups.md) and its checks on the player's machine stay open alongside this one.

Space Cadet 2026 is a definitive edition of the game: the same physics and table rules, with a modern front end, HUD and rendering on top, and a switch back to the classic game at any time, including during a game. Later phases add Full Tilt's other two tables as bonus tables.

## Decided

- **Name:** "Space Cadet 2026", with bonus tables under the same name (2026-10-20).
- **Look:** modern, but faithful to the original: its colours, its chrome-and-LED feel and its table art, not a new visual identity (2026-10-20).
- **Default:** Definitive on first launch, for existing players too: their first start after the update opens in Definitive once, with a hint that Tab switches back. Classic is one key or one menu item away (2026-10-20).
- **No online features:** no leaderboards, accounts or uploads. Records, stats and achievements stay on the player's machine (2026-10-20).
- **Toggle key:** Tab (2026-10-20). It is free in the default bindings. While a menu has the keyboard, `winmain.cpp` gives keys to ImGui, which moves focus with Tab, so menus offer the switch as an item instead.
- **The HUD is the default score panel in Definitive,** for Full Tilt data too (2026-10-20).
- **Fonts:** Exo 2 (Regular and SemiBold) for words, DSEG7 Classic Bold for numbers, and Noto Sans, Noto Sans Hebrew and Noto Sans Arabic for Greek, Hebrew and Arabic; Chinese, Japanese and Korean from a system font. Confirmed from the B1 mockups (2026-10-21).
- **Right-to-left text:** Definitive pre-shapes Hebrew and Arabic for ImGui, which does neither bidi nor shaping, and right-aligns them; the layout isn't mirrored. Classic draws them as before (2026-10-21).
- **Look of the front end:** from the B1 mockups (2026-10-21). The focused row lights a lamp like the playfield's inserts, menus sit in a column on the left so the table stays in view, Settings has its groups as tabs, and the pause screen keeps Restart and Quit to Title apart, behind a confirmation.

## Rules for every phase

- **The simulation doesn't change.** Physics, `control.cpp` and the loader stay as they are, so upstream merges stay manageable and gameplay stays faithful by construction. A step that needs a change there stops and asks first (`AGENTS.md`); Phase F's loader changes (F2) are the one planned exception, and they ask too.
- **Presentation only reads.** Definitive code reads the table through a read-only view (A2) and never calls into components or sends messages. Its menus change the options the table reads (players, rates, key bindings) only through the same option setters and `pb` entry points the Classic menus use, and input still reaches the table only through the `pb` entry points.
- **Replays match in both editions.** Every replay in `../replays/` and `../replays/fulltilt/` must match with Classic and with Definitive (A3).
- **Classic is today's game.** With Classic selected, the window, menus, score panel and frame look as they do on `main` with the same options.
- **Art comes from two places only.** Either it is computed on the player's machine from their own files (lighting, upscaling, the backdrop), or it is original work the project owns and commits (UI art, icons, menu backgrounds) under a licence that allows it, as are the fonts. Nothing traced, redrawn or exported from Microsoft's art goes into the repository, and no generated art is stored or uploaded.
- **The web build keeps up** where SDL allows it. SDL's GPU renderer doesn't run in browsers, so the web build gets the front end and HUD but not the GPU compositor (D).

## Phase A: foundation

No visible change except the switch itself.

1. **The edition switch.** A new `IntOption Edition` in `optionsStruct` (Classic 0, Definitive 1), clamped in `options.cpp`. A settings file without the key gets Definitive, so existing players also start there once, and a one-time hint names the toggle key; after that the saved choice holds. A new `ToggleEdition` binding goes last in `GameBindings`, after `ToggleUpscaledArt`, so saved and recorded bindings keep their values. Its default key is Tab. Classic's Options menu gains the same switch as its one new item, and the pause screen gets it in B4.
   - **Two presets of the presentation options.** The existing drawing options (Upscaled Art, Backdrop, Stacked Layout, Linear Filtering, Integer Scaling) are kept once per edition, so switching changes them together and back. Classic starts from today's defaults; Definitive starts from its own, such as Upscaled Art at 2×. The player can change either set. Options the table reads (rates, players, key bindings, sound) stay shared.
   - **No restart when switching.** Choosing a post effect on a renderer other than the GPU one restarts the game today (`winmain::SetPostProcessing`), and a restart loses the game in progress and ends a recording (`docs/replays.md`). So Post-Processing stays shared instead of being in the presets, and the renderer is decided once at startup: the GPU renderer first, since Definitive needs it for Phase D, else the current choice. This replaces the modernization plan's rule that the GPU renderer is created only when an effect is chosen (Phase 2 item 3). It needs SDL 3.4; with an older SDL, or when the GPU renderer can't be created, Definitive draws the table as Classic does.
   - **Done: #51.** `options::SetEdition` switches; `EditionOptionT` keeps each drawing option per edition, Classic under the old keys and Definitive under `Definitive.` keys. Upscaled Art Size is in the preset with Upscaled Art, and Definitive differs from Classic's defaults only in Upscaled Art on at 2×. The hint shows for 10 s at the first start in Definitive and names the bound key, or the menu item. Verified on Linux under Xvfb: a fresh and a pre-edition settings file both start in Definitive with the hint, Tab and the menu item switch during a game and each edition keeps its own values, a recording with Tab presses plays back, and all reference replays match. Not verified: Windows, macOS and the web build (where the GPU renderer should fail and fall back).
2. **A read-only table view.** After each update in `pb::frame`, a `TableView` struct is filled from the table: each ball's position, depth and speed, flipper angles, which lights are on or flashing and where their sprites are, the text box messages, scores, ball count, current player, mission and rank. Definitive code may include the view's header, `translations.h`, `options.h`, SDL and ImGui, but not the table's or the components' headers; strings come from `translations::GetTranslation`, which `pb::get_rc_string` calls. `tools/check-presentation-includes.sh` checks that, and lefthook and the `lint` job run it.
   - **Done: #52.** Presentation code is `SpaceCadetPinball/Definitive*.cpp` and `.h`, a file-name prefix, so `pch.h`, the include paths and the source-list hook work unchanged. The view also holds game over, demo and tilt. A ball's depth is its sprite's depth on the depth maps' scale, and a light counts as on as it is shown, timed overrides included. Mission is `lite198`'s state and Rank the lit lights of `middle_circle`, both found by group name, so `control.cpp` is unchanged. Verified on Linux: a temporary dump during the reference replays showed the expected balls, flipper angles, lights, messages, scores and rank in 3D Pinball and Full Tilt, the include check rejects table headers on scratch files, and all replays match. Nothing reads the view until A3.
3. **Replays in both editions.** `-replay` takes `-edition definitive`, which also fills the view and runs the Definitive update code headless every frame, and `tools/check-replays.sh` plays each replay in both editions. A replay's state line holds only time, mode, player, ball count, score and ball state (`docs/replays.md`), so a write to a light or a text box wouldn't show there until it changed one of those. Playback therefore also prints a hash of the view for every frame, and the check compares the two editions' hashes, so a Definitive change that touches table state fails at the first frame where the view differs. The replay format doesn't change.
   - **Done: #53.** Playback runs Classic unless `-edition definitive` is given, so its result doesn't depend on the saved settings. `DefinitiveEdition::Update` is the first presentation code and runs after each update in play and in playback; for now it only keeps the last two views. Playback prints `view <frame> <hash>` (FNV-1a over the view) to stdout only. Verified on Linux: all 17 reference replays and a recording with Tab presses match in both editions. A temporary Definitive change that wrote to a text box failed the check at the first frame it showed, while the state lines still matched. A `linux-sanitize` build passes `../replays` in both editions. Full Tilt data stops a UBSan build at a misaligned read in `GroupData::SplitSplicedBitmap`, also on the base commit; with only the alignment check off (a local build), `../replays/fulltilt` passes in both editions. Fixing that read is in loader code and needs asking. Not verified: other compilers and platforms.

Done when the switch flips during a game with nothing visibly different yet, and all replays match in both editions, also under `linux-sanitize`.

Phase A met that on Linux, with the Full Tilt alignment report above as the one exception under `linux-sanitize`. "Nothing visibly different" holds except for Definitive's own drawing defaults (Upscaled Art at 2×) and the hint, which A1 asked for.

## Phase D: compositor and lighting

This is the largest piece of engineering. Definitive draws the table through its own compositor on SDL's GPU API, which `PostEffect.cpp` already uses; Classic keeps the software frame. Without a GPU renderer (the web build, or a machine where it can't be created) Definitive draws the table as Classic does.

1. **Compositor.** The frame (1× or upscaled) and its depth map go up as textures, and the post effects run after the new passes. The software frame is still composed every frame, with the ball sprites in both editions (D3 takes them off only for the upload), so a switch shows at the next frame.
   - **Done: #66.** `Compositor` sits next to `PostEffect` on the table's side, because it needs the frame and the depth map, which presentation code can't reach. While Definitive is on and the compositor is available, `render::PresentVScreen` hands it the frame's texture and a depth texture, and it composes them into a target texture the size of the frame; `DrawSplit` and the post effect then draw that texture where they would have drawn the frame, so the nudge, the layouts and the effects work unchanged. The depth texture is the depth map of the frame on show (1× or upscaled), each depth's high byte in red and low byte in green, and only the part that sprites repainted since the last frame goes up. Every pass draws in the frame's texels, so a pass's pixel is its frame and depth texel. For now the one pass, `compose.frag.hlsl`, copies the frame texel for texel, so Definitive looks as before; D2 and D3 add to it. `PostEffect::CreateShader` picks the shader format for both. The compositor is created once per renderer like the post effects; without the GPU renderer, or if its shader or sampler can't be created, it reports itself unavailable and Definitive draws the frame as Classic does. Classic's path is unchanged. Verified on Linux under Xvfb on Vulkan (lavapipe): a temporary check read the composed texture back every frame and compared it with the software frame, with no pixel different at 1×, 2× and 4× with 3D Pinball's data and at 1× and 4× with Full Tilt's; the CRT effect draws over the composed table; the web build falls back (no GPU renderer) and shows the table and HUD in the browser preview; all replays match in both editions. Not verified: Direct3D 12 and Metal (the `.msl` is hand-written and untested), Windows and macOS builds (Actions is off on the fork, so no CI ran).
2. **Lighting from the depth maps.** Normals from the depth map, one key light, and a glow around each lit lamp, whose position and state come from the view.
   - **Done: #68.** The compose pass lights the frame. It turns each texel's depth back into a position through the table's projection (`proj::GetCamera`, a new read-only getter), takes the normal from the neighbours one table pixel away (of the two sides, the one with less change in depth, so an edge between an object and the playfield isn't a slope), and shades it with one key light from the upper left and above. The shading is divided by that of the flat playfield, so the playfield keeps its colours exactly and only slopes and rounded parts change: the near side of bumpers brightens, the far side of ramps darkens, and steep narrow parts such as rails and rims get a little extra shine. It is subtle on purpose, because the art has its lighting painted in. The glow comes from `DefinitiveScene`, new presentation code that turns the view's lit lights with a sprite into glows; the compositor draws one quad per glow into a glow texture, which the lighting pass adds. A glow takes its colour from the lamp's lit sprite (the bright texels count most), spreads from the ellipse in the sprite's rectangle with a reach capped at 9 table pixels, misses whatever stands in front of the lamp, such as a ramp, and breathes slowly (±7.5% over 2.4 s; D4's Reduced Motion turns that off). Overlapping glows keep the brightest and add half of the rest (a maximum blend in colour, the peaks summed in alpha) and are eased towards 1.5 lamps' worth, so rows of lamps don't add up to a haze. The look was reviewed in the thread from local screenshots. Verified on Linux under Xvfb on Vulkan (lavapipe): a debug view of the normals showed the flat playfield facing exactly up everywhere; lighting and glow at 1×, 2× and 4× with 3D Pinball's data; all replays match in both editions; the web build compiles with warnings as errors and keeps D1's fallback. Not verified: Direct3D 12 and Metal (`compose.frag.msl` and `glow.frag.msl` are hand-written and untested), Windows and macOS builds (no CI on the fork).

## Phase F: bonus tables

Full Tilt! Pinball's other two tables, Skulduggery (`PIRATES.DAT`) and Dragon's Keep (`DRAGON.DAT`), are in `../assets/`. They share the engine and the DAT format with Space Cadet, but their table rules live in their own executables and must be recovered with REA, likely without debug symbols, which `Pinball.exe` had. As with Space Cadet, the player supplies the files; the table list shows only the tables it finds.

1. **Get the reference files.** The zips in `../assets/` hold the 16-bit Windows 3.1 builds. Check that the CD image's Win95 folder has 32-bit `PIRATES.EXE` and `DRAGON.EXE`, as it has `CADET.EXE`, and extract each table to its own sibling folder (for example `../gamedata-skulduggery/`), recorded in the workspace `AGENTS.md`.
2. **Spike: Skulduggery without rules.** Teach `pb::SelectDatFile` the new file name, stub the rules, and see how far the engine gets: does the table draw, do the flippers and plunger work, does the ball roll right. `TPinballTable`'s constructor skips object types it doesn't know (`default: continue`), so log those. Look for Space Cadet assumptions outside `control.cpp` too. The spike ends in a short report with the cost of the rest. Any loader change it needs is the exception named under the rules above, so it asks first.
3. **Decide the rules layout.** `control.cpp` is Space Cadet's rules, and the rule "table rules live only in `control.cpp`" assumes one table. Proposal: Space Cadet stays in `control.cpp`, each bonus table gets its own `control_<table>.cpp`, and the table picks its rules at load. Decide before writing any rules, then update that convention in `AGENTS.md`.
4. **Rules from the executable,** one mission or feature per pull request, each checked against the table's `.EXE` with REA, with reference replays recorded per table in `../replays/<table>/`.
5. **Table select** in the main menu. High scores and resolution are kept per table (#27, #36), but `options::TableKeyPrefix` knows only Space Cadet, Full Tilt and the Full Tilt demo, so each bonus table gets its own prefix. Classic shows each table as Full Tilt did.
6. **Dragon's Keep** follows the same steps once Skulduggery plays.
