# Space Cadet 2026 plan

Date: 2026-10-20. Status: not started. The modernization stack is merged ([modernization plan](2026-10-18-modernization.md)); item 16 of [the follow-ups plan](2026-10-19-follow-ups.md) and its checks on the player's machine stay open alongside this one.

Space Cadet 2026 is a definitive edition of the game: the same physics and table rules, with a modern front end, HUD and rendering on top, and a switch back to the classic game at any time, including during a game. Later phases add Full Tilt's other two tables as bonus tables.

## Decided

- **Name:** "Space Cadet 2026", with bonus tables under the same name (2026-10-20).
- **Look:** modern, but faithful to the original: its colours, its chrome-and-LED feel and its table art, not a new visual identity (2026-10-20).
- **Default:** Definitive on first launch; Classic is one key or one menu item away (2026-10-20).
- **No online features:** no leaderboards, accounts or uploads. Records, stats and achievements stay on the player's machine (2026-10-20).
- **Toggle key:** Tab (2026-10-20). It is free in the default bindings. While a menu has the keyboard, `winmain.cpp` gives keys to ImGui, which moves focus with Tab, so menus offer the switch as an item instead.
- **The HUD is the default score panel in Definitive,** for Full Tilt data too (2026-10-20).

## Rules for every phase

- **The simulation doesn't change.** Physics, `control.cpp` and the loader stay as they are, so upstream merges stay manageable and gameplay stays faithful by construction. A step that needs a change there stops and asks first (`AGENTS.md`); Phase F's loader changes (F2) are the one planned exception, and they ask too.
- **Presentation only reads.** Definitive code reads the table through a read-only view (A2) and never calls into components or sends messages. Its menus change the options the table reads (players, rates, key bindings) only through the same option setters and `pb` entry points the Classic menus use, and input still reaches the table only through the `pb` entry points.
- **Replays match in both editions.** Every replay in `../replays/` and `../replays/fulltilt/` must match with Classic and with Definitive (A3).
- **Classic is today's game.** With Classic selected, the window, menus, score panel and frame look as they do on `main` with the same options.
- **Art comes from two places only.** Either it is computed on the player's machine from their own files (lighting, upscaling, the backdrop), or it is original work the project owns and commits (UI art, icons, menu backgrounds) under a licence that allows it, as are the fonts. Nothing traced, redrawn or exported from Microsoft's art goes into the repository, and no generated art is stored or uploaded.
- **The web build keeps up** where SDL allows it. SDL's GPU renderer doesn't run in browsers, so the web build gets the front end and HUD but not the GPU compositor (D).

## Phase A: foundation

No visible change except the switch itself.

1. **The edition switch.** A new `IntOption Edition` in `optionsStruct` (Classic 0, Definitive 1), clamped in `options.cpp`. A new settings file gets Definitive and a one-time hint naming the toggle key; whether existing settings files switch too is an open question. A new `ToggleEdition` binding goes last in `GameBindings`, after `ToggleUpscaledArt`, so saved and recorded bindings keep their values. Its default key is Tab. Classic's Options menu gains the same switch as its one new item, and the pause screen gets it in B4.
   - **Two presets of the presentation options.** The existing drawing options (Upscaled Art, Backdrop, Stacked Layout, Linear Filtering, Integer Scaling) are kept once per edition, so switching changes them together and back. Classic starts from today's defaults; Definitive starts from its own, such as Upscaled Art at 2×. The player can change either set. Options the table reads (rates, players, key bindings, sound) stay shared.
   - **No restart when switching.** Choosing a post effect on a renderer other than the GPU one restarts the game today (`winmain::SetPostProcessing`), and a restart loses the game in progress and ends a recording (`docs/replays.md`). So Post-Processing stays shared instead of being in the presets, and the renderer is decided once at startup: the GPU renderer first, since Definitive needs it for Phase D, else the current choice. This replaces the modernization plan's rule that the GPU renderer is created only when an effect is chosen (Phase 2 item 3). It needs SDL 3.4; with an older SDL, or when the GPU renderer can't be created, Definitive draws the table as Classic does.
2. **A read-only table view.** After each update in `pb::frame`, a `TableView` struct is filled from the table: each ball's position, depth and speed, flipper angles, which lights are on or flashing and where their sprites are, the text box messages, scores, ball count, current player, mission and rank. Definitive code may include the view's header, `translations.h`, `options.h`, SDL and ImGui, but not the table's or the components' headers; strings come from `translations::GetTranslation`, which `pb::get_rc_string` calls. `tools/check-presentation-includes.sh` checks that, and lefthook and the `lint` job run it.
3. **Replays in both editions.** `-replay` takes `-edition definitive`, which also fills the view and runs the Definitive update code headless every frame, and `tools/check-replays.sh` plays each replay in both editions. A replay's state line holds only time, mode, player, ball count, score and ball state (`docs/replays.md`), so a write to a light or a text box wouldn't show there until it changed one of those. Playback therefore also prints a hash of the view for every frame, and the check compares the two editions' hashes, so a Definitive change that touches table state fails at the first frame where the view differs. The replay format doesn't change.

Done when the switch flips during a game with nothing visibly different yet, and all replays match in both editions, also under `linux-sanitize`.

## Phase B: front end

Definitive replaces the menu bar and dialogs; Classic keeps them unchanged. Everything works with keyboard, mouse, gamepad and touch.

1. **Visual language.** A small set of tokens (colours from the table's own palette: deep space blue, chrome, the orange and red of its LEDs; spacing; openly licensed typefaces) and an ImGui theme built from them. Proposed fonts, all under the SIL Open Font License, committed with their licences in `third_party/` and embedded, and added to `third_party/README.md` and the vendored-code gotcha in `AGENTS.md`:
   - **Exo 2** for menus, headings and HUD text: a geometric sans with a space-age feel that stays readable at small sizes. It covers Latin and Cyrillic.
   - **DSEG7 Classic** for scores and other numbers: seven-segment digits, close to the original panel's LED score.
   - **Noto Sans** for Greek, **Noto Sans Hebrew** and **Noto Sans Arabic**, merged into the same ImGui font for the scripts Exo 2 lacks. Check how the current Arabic and Hebrew strings render first, because ImGui does no shaping or bidi.
   - **Chinese, Japanese and Korean** come from a system font (or the existing Font File option), not an embedded one: Noto Sans CJK is about 16 MB a weight, several times the whole 3.4 MB web build. Look for Microsoft YaHei, Yu Gothic and Malgun Gothic on Windows, PingFang and Hiragino on macOS, and Noto Sans CJK on Linux.

   Mockups first, as HTML previews, reviewed before code.
2. **Title screen and main menu.** Demo mode plays behind the title. Menu: Play, Players (1 to 4), Table (from Phase F), Settings, Controls, Records, Credits, Quit (no Quit on the web).
3. **Settings,** grouped into Edition, Display, Graphics, Audio, Controls and Accessibility, with the effect of each change visible behind the menu. Key binding uses the scancode bindings from #38.
4. **In-game screens:** a pause overlay (Resume, Restart, Settings, Mission Guide, Classic/Definitive, Quit to Title), the game-over summary per player, and high-score name entry that a gamepad can use.
5. **Finding the game data on the desktop.** Today a missing DAT file ends in an error box (`winmain.cpp`). Definitive shows a first-run screen instead: it lists the places it looked, lets the player choose a folder (`SDL_ShowOpenFolderDialog`) and remembers the path. Nothing is copied.

Done when a new player can go from first start to a game, change settings, pause, finish and enter a high score without the menu bar, in both the desktop and web builds.

## Phase C: HUD

1. **The Definitive score panel,** the default in Definitive. Drawn as vector text beside or under the table, using the layout from `render::BoardRect` and `SidebarRect`: score, ball, every player's score, the current mission and what it needs next, and the rank. It shows the same messages as the original text boxes, through `pb::get_rc_string`. New labels get new `Msg` entries in `translations.cpp`, so they need translations for every language the game has; until then they fall back to English.
2. **Mission Guide.** A pause screen that explains each mission and rank, written for this project from what `control.cpp` does. It's the part of the game most players never understood.
3. **Full Tilt data** gets the same HUD by default, although its panel has a different width and three resolutions.

Done when the HUD shows the same information as the panel throughout the reference replays, in each language, and the panel is back the moment Classic is selected.

## Phase D: compositor and lighting

This is the largest piece of engineering. Definitive draws the table through its own compositor on SDL's GPU API, which `PostEffect.cpp` already uses; Classic keeps the software frame. Without a GPU renderer (the web build, or a machine where it can't be created) Definitive draws the table as Classic does.

1. **Compositor.** The frame (1× or upscaled) and its depth map go up as textures, and the post effects run after the new passes. The software frame is still composed every frame, without the ball sprites while Definitive is on (D3) and with them in Classic, so a switch shows at the next frame.
2. **Lighting from the depth maps.** Normals from the depth map, one key light, and a glow around each lit lamp, whose position and state come from the view.
3. **The ball.** Definitive composes the frame without the ball sprites and draws each ball as a shaded, reflective sphere with a contact shadow, depth-tested against the depth texture so ramps and walls still cover it. When FPS is above UPS it uses the interpolated positions (modernization plan, Phase 2 item 5); at the default 60 frames and 120 updates a second, it uses each ball's position after the last update, as Classic does.
4. **Options:** each effect has its own switch under Graphics (B3), and Reduced Motion turns off the glow pulse and screen motion.

Done when lighting and the ball look right on the whole table at 1×, 2× and 4×, the switch to Classic shows the exact Classic frame, and the replays match. Check on Vulkan here, and on Direct3D 12 and Metal on the player's machines (as follow-ups item 3).

## Phase E: polish

1. **Portrait and cabinet modes:** the table rotated for vertical monitors and phones.
2. **Accessibility:** larger UI text, high-contrast HUD, colour choices that don't depend on red and green, and Reduced Motion everywhere.
3. **Local stats and achievements,** worked out from what the view reports (missions finished, ranks reached, balls saved). Stored next to the high scores, never uploaded.
4. **Audio:** optional room reverb and wider stereo. Sound packs load from the preferences folder, as sprite overrides do, and stay on the player's machine.
5. **Recording viewer:** play back a recorded game with a timeline, using the existing replay format. The player sees it as "Recordings", because a Replay is the free game the table awards (`GLOSSARY.md`).

## Phase F: bonus tables

Full Tilt! Pinball's other two tables, Skulduggery (`PIRATES.DAT`) and Dragon's Keep (`DRAGON.DAT`), are in `../assets/`. They share the engine and the DAT format with Space Cadet, but their table rules live in their own executables and must be recovered with REA, likely without debug symbols, which `Pinball.exe` had. As with Space Cadet, the player supplies the files; the table list shows only the tables it finds.

1. **Get the reference files.** The zips in `../assets/` hold the 16-bit Windows 3.1 builds. Check that the CD image's Win95 folder has 32-bit `PIRATES.EXE` and `DRAGON.EXE`, as it has `CADET.EXE`, and extract each table to its own sibling folder (for example `../gamedata-skulduggery/`), recorded in the workspace `AGENTS.md`.
2. **Spike: Skulduggery without rules.** Teach `pb::SelectDatFile` the new file name, stub the rules, and see how far the engine gets: does the table draw, do the flippers and plunger work, does the ball roll right. `TPinballTable`'s constructor skips object types it doesn't know (`default: continue`), so log those. Look for Space Cadet assumptions outside `control.cpp` too. The spike ends in a short report with the cost of the rest. Any loader change it needs is the exception named under the rules above, so it asks first.
3. **Decide the rules layout.** `control.cpp` is Space Cadet's rules, and the rule "table rules live only in `control.cpp`" assumes one table. Proposal: Space Cadet stays in `control.cpp`, each bonus table gets its own `control_<table>.cpp`, and the table picks its rules at load. Decide before writing any rules, then update that convention in `AGENTS.md`.
4. **Rules from the executable,** one mission or feature per pull request, each checked against the table's `.EXE` with REA, with reference replays recorded per table in `../replays/<table>/`.
5. **Table select** in the main menu. High scores and resolution are kept per table (#27, #36), but `options::TableKeyPrefix` knows only Space Cadet, Full Tilt and the Full Tilt demo, so each bonus table gets its own prefix. Classic shows each table as Full Tilt did.
6. **Dragon's Keep** follows the same steps once Skulduggery plays.

## Working order

Phases run in order A, B, C, D, E, F as a stack of pull requests, one per numbered item, each keeping CI green and the replays matching in both editions. B and C can start once A2 is merged, though C2's Mission Guide needs B4's pause screen. D needs A, and D4 needs B3's Graphics and Accessibility groups. F1 can run at any time; the F2 spike too, as long as nothing from it merges without asking.
